# 01. Waterfall Model

## 📚 Introduction

Before Agile and DevOps became popular, many organizations followed traditional software development approaches.

One commonly used approach was the **Waterfall Model**.

The Waterfall Model follows a sequential approach where one phase is completed before moving to the next phase.

---

## 🔄 Waterfall Model

The typical flow is:

Requirements
↓
Design
↓
Development
↓
Testing
↓
Deployment
↓
Maintenance

---

## 1️⃣ Requirements

The customer provides the requirements.

The Business Analyst and other teams collect and document the requirements.

Example:

For a Banking Application, requirements may include:

- Customer Login
- Account Balance
- Fund Transfer
- Transaction History
- Loan Services

---

## 2️⃣ Design

Once requirements are finalized, the application architecture and design are prepared.

This may include:

- Application Architecture
- Database Design
- UI Design
- Network Design

---

## 3️⃣ Development

Developers start writing the application code based on the approved requirements and design.

---

## 4️⃣ Testing

After development is completed, the application is handed over to the testing team.

Testers perform activities such as:

- Functional Testing
- Integration Testing
- System Testing
- Bug Identification

---

## 5️⃣ Deployment

After testing and approvals, the application is deployed to the production environment.

---

## 6️⃣ Maintenance

After deployment, the application is maintained and issues are fixed.

---

# ❌ Challenges of the Waterfall Model

### 1. Requirement Changes

Once requirements were finalized, changing them later could be difficult and expensive.

### 2. Late Testing

Testing generally happened after development was completed.

Because of this, defects could be discovered late.

### 3. Late Customer Feedback

Customers generally saw the working application much later in the development lifecycle.

### 4. Long Release Cycle

The complete application could take a long time before reaching production.

### 5. Higher Risk

If a problem was discovered late in the lifecycle, fixing it could require significant rework.

---

## 💡 Example

Imagine a bank asks for a new banking application.

The team spends several months:

Requirements → Design → Development → Testing

After several months, the customer says:

> "We need an additional feature."

In a traditional sequential process, accommodating such changes could require significant rework.

This created a need for a more flexible development approach.

---

## 👉 Next Step

To address some of these challenges, organizations increasingly adopted **Agile development practices**.
